# Проверка SNS CHAT v2.41

Проверен присланный JS размером 612 999 байт. Синтаксис корректен. Есть хорошая база: работа ограничена viewtopic.php и ForumID=4, очередь допускает максимум два активных запроса и разносит их старты минимум на секунду, есть обработка 429/503, история подгружается при прокрутке, реакции не опрашиваются постоянным интервалом.

## Подтверждённые проблемы

1. **Палитра реакций заранее создаётся для каждого сообщения** (исходные строки 3079–3105). На DOM-макете со 100 сообщениями: 3 000 кнопок выбора и 12 400 обработчиков внутри сообщений. Это измерение количества узлов/обработчиков в jsdom, не FPS и не замер реального браузера.
2. **Обновление аватара вызывает полную переобработку сообщений** (4589–4591). `SNSUserVisual`-событие вызывает `SNSEnhancePosts()` без аргумента; эта функция передаёт `true` в `enhancePosts`, обходя кэш обработанного контента. События отправляются из обновлений отдельных аватаров (7574 и 8364). Нужно передавать изменённый пост и объединять события в один проход. Пока не изменено.
3. **Поиск перестраивает индекс при каждом запуске** (8110–8158, 9814). Он снова разбирает HTML сохранённых страниц и клонирует сообщения, затем фильтрует весь индекс. Задержка 120 мс лишь объединяет быстрые нажатия; она не кэширует индекс. Нужен индекс, обновляемый при загрузке истории/публикации/правке/удалении. Пока не изменено.
4. **Механизм скрытой вкладки не подключён к запросам очереди** (72, 125–126): `snsBackground` только читается и удаляется в scheduler; ни один вызов не передаёт `snsBackground: true`. На макете GET без флага отправился при `document.hidden=true`. Отдельная загрузка реакций сама проверяет скрытую вкладку; поэтому нельзя говорить, что абсолютно все фоновые операции продолжаются. Нужно классифицировать фоновые чтения, оставив сохранение/отправку доступными. При включении флага учесть, что queued-запросы сейчас отменяются через 20 секунд.
5. **Частые опросы загрузчиков изображений** (2103–2110 и 5374–5396): каждые 120 мс до ~30 секунд и каждые 100 мс до ~120 секунд соответственно. Они запускаются при действиях пользователя, а не постоянно в простое. Лучше события/наблюдение за результатом с ограниченным fallback. Пока не изменено.

## Минимальная проверенная правка

`lazy-reactions.patch` меняет только создание палитры: кнопки выбора создаются при первом открытии соответствующей палитры. Не меняет алгоритм записи реакции, данные, оформление или остальные функции.

На том же макете со 100 сообщениями после правки, до открытия палитр: 0 кнопок выбора и 400 обработчиков внутри сообщений. Проверено: открытие, закрытие, повторное открытие без дублей, переключение между палитрами, выбор реакции с отображением чипа и вызовом storage.set. Оба полных JS проходят проверку синтаксиса. Ответ сервера на запись не имитировался как успешный: это проверка вызова, не подтверждение сохранения на реальном RusFF.

Патч рассчитан на исходный присланный v2.41. Для применения сохраните код в `sns.js` и выполните `git apply lazy-reactions.patch` в каталоге файла. Либо перенесите изменения по сравнению в патче в редакторе. Не подключайте оригинал и исправленную копию одновременно.

## Ограничения

Это анализ кода и локальная проверка изолированного блока реакций, а не полный запуск чата на RusFF, сетевой нагрузочный тест или профиль CPU/памяти телефона. Не объявляю весь SNS лёгким после одной правки. Следующие приоритеты: обновления аватаров и кэш поиска.

Некоторые большие observer/history-функции в исходнике определены, но не имеют вызовов в этом файле (`installPublishedNoticeObserver`, три `installObserver`, `syncAllPages`). Их наличие само по себе не доказывает активный опрос или наблюдение. Поэтому они не представлены как подтверждённые источники текущей нагрузки.
